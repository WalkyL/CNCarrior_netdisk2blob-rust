# 历史对象收敛与容量 / 缓冲预算

这份文档专门说明内容策略变化之后，历史对象如何安全收敛，以及这件事对:

- 目标云盘容量
- 原云盘旧副本
- 本地 spool 磁盘
- Admin 执行前预检

分别意味着什么。

如果你只想先看系统总体资源预算，去看:

- [docs/resource-budget.md](./resource-budget.md)

如果你想先看总体架构边界，去看:

- [docs/architecture.md](./architecture.md)

如果你只想先看当前控制面 / API 已经公开了什么，去看:

- [docs/object-actions-api-reference.md](./object-actions-api-reference.md)

## 1. 先定死的产品规则

### 1.1 历史对象不会自动迁移

内容策略变化默认只影响:

- 新写入
- 后续覆盖写

历史对象不会偷偷发生下面这些变化:

- 自动补新副本
- 自动删除旧副本
- 自动迁移 home provider
- 自动加密重写
- 自动解密重写
- 自动切换加密 profile

这些动作都必须是:

1. 先预览
2. 再显式执行
3. 全程可审计

### 1.2 容量未知时默认阻断

只要显式收敛涉及写入目标云盘，就必须先做容量预检。

规则是:

- 目标容量明确不足: 阻断
- 目标容量拿不到: 默认阻断
- 本地 spool 预算明确不足: 阻断
- 任何阻断都不能先改 placement、也不能先删旧副本

### 1.3 删除一定后置

任何“新增副本 + 删除旧副本”的收敛都必须遵守:

1. 先把新目标写成功
2. 再更新元数据
3. 最后才允许删除旧副本

如果新目标没写成:

- placement 不变
- home provider 不变
- 旧副本不删
- 不允许出现“写了一半但元数据已经切走”的状态

## 2. 需要同时看的三类空间

历史对象收敛时，不能只看“目标云盘还有多少剩余空间”，至少要同时看三件事:

### 2.1 目标云盘最终需要多少空间

这是对象收敛完成后，新对象在目标云盘最终占用的空间。

记号:

- `stored_size_current`: 当前对象在现有 home provider 上的落盘体积
- `stored_size_target`: 收敛后对象在目标 provider 上的落盘体积

注意:

- 明文对象时，`stored_size_target` 通常接近原文件大小
- 加密对象时，`stored_size_target` 必须按加密后的真实落盘体积计算
- 不能拿明文 30 GiB 去判断加密后写入是否放得下

### 2.2 目标云盘峰值需要多少空间

有些操作不是“覆盖写”，而是“两阶段写新对象，再切换，再删旧对象”。

这时要看峰值空间，不是只看最终空间。

典型场景:

- 同云盘同 key 的加密重写
- 同云盘同 key 的解密重写
- 同云盘切换加密 profile

这类路径不能原地边读边覆盖，否则失败时容易把对象打坏。

保守规则:

- 同 provider、同 key 的重写，必须走临时 key / 临时对象
- 因此 provider 侧峰值空间应按:

`peak_remote_bytes ~= stored_size_current + stored_size_target`

来预算

### 2.3 本地 spool 需要多少空间

即使 provider 之间的数据迁移可以逻辑上“流式转发”，本地节点仍可能因为这些原因需要磁盘缓冲:

- S3 签名路径需要先落盘再验哈希
- provider 上传要求预分片 / 预回放
- provider SDK 或适配层暂时还不是全链路流式
- 显式收敛执行器需要把同一对象安全回放到另一个目标

因此部署时必须给本地磁盘单独做预算，不能把它和 provider 容量混为一谈。

## 3. 各种场景怎么判断

### 3.1 从 A 云盘给历史对象新增 C 副本

例子:

- 当前对象只在 `A`
- 现在策略改成要写 `A + C`
- 该对象大小约 `30 GiB`
- `C` 只有 `20 GiB` 空闲

规则:

- 这个对象对 `C` 的显式补副本必须阻断
- 不能因为 `A` 还在，就把元数据写成“已经符合新策略”
- 不能先把旧记录删掉再说

判断标准:

`free(C) >= stored_size_target_on_C`

否则直接阻断

### 3.2 从 A 迁移 home provider 到 B，并改成加密写入

例子:

- `A` 上已经有 `30 GiB` 明文对象
- 现在想迁到 `B`
- `B` 看起来也有 `30 GiB` 空闲
- 但加密后真实落盘会比明文稍大

规则:

- 预检必须按 `stored_size_target` 判断，而不是按 `30 GiB` 明文判断
- 如果 `B` 放不下加密后的对象，就必须阻断

判断标准:

`free(B) >= encrypted_stored_size_target`

不满足就不能开始执行

### 3.3 从 A+B 改成 A+C

这类场景最容易让人误以为系统会“自动把旧对象补到 C，再把 B 清掉”。

这里要明确:

- 不会自动发生
- 必须显式收敛

显式收敛时的顺序应当是:

1. 先检查 `C` 是否放得下
2. 写入 `C`
3. 更新该对象的保护计划 / 副本计划元数据
4. 最后才允许把 `B` 的旧副本删除

如果 `C` 不够空间:

- `B` 不能先删
- 不能把对象留成只有 `A` 一份却误标成 `A+C`

### 3.4 同一个 provider 上做加密重写

例子:

- `B` 上已有明文对象
- 现在想把它改写成加密对象
- key 还不变

这是最危险的一类，因为它不能原地覆盖。

必须按两阶段思路处理:

1. 读取旧对象
2. 写出临时新对象
3. 校验新对象
4. 切换到正式 key
5. 删除旧对象 / 临时对象

所以 provider 侧峰值空间预算必须按:

`stored_size_current + stored_size_target`

计算

如果 provider 当下空闲空间连这个峰值都不够:

- 不允许开始

### 3.5 取消加密

从加密改回明文也一样不能掉以轻心。

虽然最终对象可能更小，但执行过程中仍然可能需要:

- 旧密文对象继续保留
- 新明文对象先写成功
- 最后再切换和清理

因此也应按两阶段执行，并提前检查:

- provider 峰值空间
- 本地 spool 空间

## 4. 本地 spool 怎么预算

## 4.1 理想情况

理想路径是:

- 源端流式读
- 中间只保留有界 chunk
- 目标端流式写

这时本地 spool 近似只需要:

`peak_local_spool ~= O(chunk_window)`

通常应是 MiB 级，而不是整对象级。

## 4.2 一侧需要整对象回放

如果源端或目标端有一侧必须先整对象落盘，再回放:

`peak_local_spool ~= max(stored_size_current, stored_size_target)`

常见于:

- 需要预哈希
- 需要预分片规划
- 需要重复读取同一对象流

## 4.3 两侧都需要整对象回放

如果源端和目标端都不能真正流式直通，而是都要求整对象级回放，那么本地 spool 峰值要按更保守的上界算:

`peak_local_spool ~= stored_size_current + stored_size_target`

这类场景对小机器非常危险，必须在执行前显式阻断或降并发。

## 4.4 多对象并发

如果同时跑多个显式收敛任务，本地 spool 总需求近似为:

`peak_local_spool_total ~= Σ each_in_flight_object_peak_local_spool`

部署建议:

- 给显式收敛使用独立 spool 目录
- 不要和系统 overlay、日志目录混在一起
- 预留至少 `20%` 的保护余量

保守部署公式:

`recommended_free_spool >= concurrent_peak_local_spool_total * 1.2`

## 5. Admin 预检应该给用户看到什么

无论最终执行入口落在哪个 tab，预检都应明确展示这些量:

- 当前 home provider
- 目标 home provider
- 当前是否加密
- 目标是否加密
- 当前加密 profile
- 目标加密 profile
- 需要新增哪些副本
- 需要删除哪些副本
- 目标 provider 最终需要的空间
- 目标 provider 峰值需要的空间
- 本地 spool 预算上界
- 阻断原因

阻断原因至少要能区分:

- 目标 provider 空间不足
- 目标 provider 容量未知
- 本地 spool 空间不足
- 对象缺少 application_id / content-type 等关键上下文
- 当前 provider 不支持安全两阶段重写

## 6. 目前推荐的执行策略

在显式收敛执行路径完全落地前，先固定这些策略:

### 6.1 新增副本

- 只新增，不删旧
- 先确保新目标写成功
- 成功后再更新保护计划

### 6.2 迁移 home provider

- 新 home 写成功前，不切换 placement
- 新 home 写成功后，再更新 placement
- 旧 home 删除必须最后做

### 6.3 加密 / 解密 / profile 切换

- 必须显式执行
- 必须先算出 `stored_size_target`
- 同 provider 同 key 必须使用临时对象两阶段
- 任一空间预算不满足就阻断

## 7. 对运维和部署的直接要求

如果宿主机要承载:

- 大对象显式迁移
- 历史对象补副本
- 加密重写

则部署前至少要确认:

1. provider 健康页能看到尽可能准确的容量信息
2. `CCBG_BODY_SPOOL_DIR` 指向独立可写卷
3. `CCBG_MAX_SPOOLED_OBJECT_BYTES` 与预期对象体积相匹配
4. 当前宿主的 spool 卷剩余空间足够
5. 显式收敛任务默认低并发执行
6. 小内存 / 小磁盘设备不要并发跑大对象收敛

对 `OpenWRT`、`N100`、小型 `arm64` 软路由尤其要保守:

- 不要默认并发迁移大对象
- 不要假设“云盘够大，本地就一定扛得住”
- 先看本地 spool，再看远端 provider

## 8. 一句话总结

历史对象收敛不是“改个策略就会自己变好”。

它本质上是一类显式数据迁移任务，必须同时满足:

- 目标云盘最终空间够
- 目标云盘峰值空间够
- 本地 spool 空间够
- 执行顺序可回滚
- 旧副本删除后置

只要其中任何一项不确定，就应默认阻断，而不是赌它会成功。
